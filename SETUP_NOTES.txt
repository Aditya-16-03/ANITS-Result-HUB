 STEP 3 - FRONTEND NOT CONNECTING TO BACKEND (2 root causes)
==========================================================================

PROBLEM A: Frontend pointed to a REMOTE backend
- File: ANITS-Results-Hub-Frontend-main/.env
- NEXT_PUBLIC_BACKEND_URL was set to a deployed URL
  (https://harsha.vivek275.rocks/) instead of the local server.
- FIX: changed it to  NEXT_PUBLIC_BACKEND_URL=http://localhost:8091
- Why it matters: Axios uses this as its baseURL (src/services/api.ts).
  Variables prefixed NEXT_PUBLIC_ are exposed to the browser in Next.js.

PROBLEM B: Backend CORS was effectively broken for local use
- File: ANITS-Results-Hub-Backend-main/.../security/SecurityConfig.java
- The security config had `.cors(cors -> {})` but NO CorsConfigurationSource
  bean. The `spring.web.cors.*` lines in application.properties are NOT
  real Spring Boot config keys, so they were being ignored.
- With `anyRequest().authenticated()`, the browser's pre-flight OPTIONS
  request (sent automatically before cross-origin POST/GET) was getting
  rejected, blocking every API call from the browser.
- FIX (in SecurityConfig.java):
    1. Added a CorsConfigurationSource bean that allows any localhost /
       127.0.0.1 port, with methods GET/POST/PUT/DELETE/OPTIONS/PATCH,
       all headers, and credentials enabled.
    2. Permitted pre-flight requests explicitly:
       .requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()
- VERIFIED: an OPTIONS pre-flight from http://localhost:9002 returned
  HTTP 200 with the correct Access-Control-Allow-Origin header, and the
  Spring Security filter chain now includes CorsFilter.

INTERVIEW TALKING POINTS (CORS):
- CORS = browser security that blocks cross-origin requests unless the
  server opts in via Access-Control-Allow-* headers.
- A "pre-flight" is an automatic OPTIONS request the browser sends to
  ask permission before the real request when it's "non-simple".
- In Spring Security, CORS must be handled BEFORE authentication, which
  is why a proper CorsConfigurationSource bean (or permitAll on OPTIONS)
  is required - otherwise pre-flight gets 401/403.

 STEP 5 - "REGISTRATION FAILED - Status 500" (NOT a connection bug)
==========================================================================
- Once connected, sign-up returned 500 with message "Not a Valid User".
- Root cause (by design, not a code bug):
    * RegisterController -> UserValidationService.isValidStudent()
    * It checks that the student's roll number ALREADY EXISTS in a table
      named dynamically:  students_<rollPrefix>_<department>
    * For roll A23126552069 + dept CSM  ->  table "students_a23_csm"
      (rollPrefix = first 3 chars of roll = "a23", dept lowercased).
- The app's intended flow: an ADMIN first uploads a student-details Excel,
  which dynamically CREATEs and populates that table (Apache POI parses the
  file, builds the table from column headers, roll_no as PRIMARY KEY).
- A fresh DB has no such table/data -> validation fails -> 500.

FIX APPLIED (to unblock local testing):
- Manually created the table and seeded the student record:
    Table : students_a23_csm (roll_no PK, name_of_the_student, section)
    Row   : A23126552069 | Badiganti Aditya Vardhan | A
- Re-tested sign-up -> 200 {"success":true,"typeOfUser":"student"}.
- The account is now stored in the "users" table, so login works.

INTERVIEW TALKING POINTS (this design):
- The app uses DYNAMIC/runtime table creation per batch+branch instead of
  fixed entity tables - flexible for varied Excel formats but bypasses JPA
  and uses raw JdbcTemplate SQL (note: string-built SQL = SQL-injection
  risk; a production version should validate/whitelist table names).
- Registration is gated on pre-loaded official records, so only genuine
  students/faculty can create accounts.
